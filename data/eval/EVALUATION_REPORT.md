# KG-RAG Evaluation Report

## 1. Overview

This document summarizes the evaluation of the KG-RAG system across two
configurations (B and C) using the PrimeKG drug-disease dataset. The evaluation
measures how well each configuration retrieves and generates answers about
drug-disease relationships (contraindication, indication, off-label use) under
controlled knowledge availability conditions.

### System Configurations

| Config | Description | Primary LLM | Validation LLM | Key Behavior |
|--------|-------------|-------------|----------------|--------------|
| **B** (without-validation) | Agent with KG tools, no validation | Varies by run | None | Retrieves facts from KG; refuses if insufficient |
| **C** (with-validation) | Agent + dual-LLM validated expansion | Varies by run | gemma-4-31b-it | Proposes missing triplets, validates with remote LLM, persists accepted ones |

### Dataset

| Aspect | Value |
|--------|-------|
| Source | PrimeKG drug-disease subset (`data/kg_drug_disease.csv`, ~43 K rows) |
| Drug-aware sample | `--max-rows 1000` ⇒ 970 rows actually surviving (drug groups are kept whole) |
| Per-relation split | `--test-ratio 0.20` (entity-disjoint per relation) |
| Tier ratio | `--full-ratio 0.30` ⇒ 30 % Full / 70 % Partial of multi-triple test drugs |
| Held-out fraction | `--partial-include 0.50` ⇒ ⌊50 %⌋ of each Partial drug's triples in train, rest held out |
| Seed | `42` (drives all sampling, shuffling, and held-out selection) |
| Train set (Neo4j) | 884 triples (background drugs + Full-tier drugs + Partial-tier `kg_answers`) |
| Test set (QA source) | 221 triples (every gold triple for every test drug) |
| QA dataset | 194 questions (53 Full-tier, 141 Partial-tier) generated by gemma-4-31b-it |
| Relations | contraindication (114) · indication (58) · off-label use (22) |
| Directions | forward (drug → diseases) and reverse (disease → drugs) |

The exact hyperparameter values above are also persisted in
[`split_stats.json`](split_stats.json), which the evaluator embeds in
each report under `report["split_stats"]` and uses to derive the
`f30_p70` block in the auto-generated report filename.

### Evaluation Tiers

| Tier | Share | Neo4j coverage | What `tier_assignments.json` says | Purpose |
|------|-------|----------------|-----------------------------------|---------|
| **Full**    | 30 % (53 questions)  | 100 % of drug's triples in `train.csv` | `kg_answers = gold_answers`, `held_out_answers = []` | Baseline -- can the system retrieve what's already there? |
| **Partial** | 70 % (141 questions) | Subset of drug's triples in `train.csv` | `kg_answers ⊊ gold_answers`, `held_out_answers ≠ []` | Core test -- can Config C recover the held-out answers via dual-LLM validation? |

### Primary Metric

**Gold Recall** (mean): Fraction of ALL gold answers found in the prediction,
averaged across questions. This replaced the earlier Exact Match (binary) and
KG Recall (KG-only) metrics with a single measure that captures both retrieval
completeness and answer quality.

## 4. Definitive Comparison: Config B vs Config C

Using Run 2 Config B and Run 3 Config C (same primary model
`gemma-4-26b-a4b-it`, same clean Neo4j, both 194/194 scored):

| Metric | Config B | Config C | Delta |
|--------|----------|----------|-------|
| **Gold Recall** | 0.6686 | **0.7198** | **+0.0512 (+7.7%)** |
| **Answer Rate** | 0.9021 | **0.9845** | **+0.0824 (+9.1%)** |
| **Hallucination** | 0.0009 | **0.0004** | **-0.0005 (-56%)** |
| **Latency (s)** | 23.1 | 172.8 | +149.8 |

### Where Config C Wins

**Off-label use (+36.1pp Gold Recall, +61.2% relative)**: Config C improved
from 0.589 to 0.950. Off-label relationships are the sparsest in the KG, so
Config C's ability to propose and validate missing triplets is most valuable
here. In the partial tier specifically, Config C scored 15/19 perfect
(GR=1.00) vs Config B's 9/19.

**Partial tier (+7.1pp Gold Recall)**: On questions where the KG is
deliberately incomplete, Config C recovered more gold answers (0.618 vs 0.548)
and answered 97.9% of questions vs Config B's 86.5%.

**Answer Rate (+8.2pp overall)**: Config C refuses to answer far fewer
questions because the validation loop often recovers enough information to
generate a response even when initial retrieval is insufficient.

**Hallucination (-56%)**: Config C's validated triplets provide better grounding,
reducing the already-low hallucination rate by more than half.

### Where They Tie

**Full tier (both ~0.99 GR)**: When all gold answers are in the KG, both
configs perform near-perfectly, confirming the retrieval pipeline works well.

**Contraindication (both ~0.655 GR)**: The most common relation type has
sufficient KG coverage that validation adds no benefit.

### The Tradeoff

**Latency (7.5x slower)**: Config C averages 173s per question vs Config B's
23s. The validation round-trips (propose -> validate -> re-assess -> answer ->
persist) are the dominant cost. On the free API tier, rate limits further
inflate this.

## 5. Impact of Agent Fixes (Run 1 -> Run 2)

Several agent-level fixes were implemented between Run 1 and Run 2:

### 5.1 Log Interleaving Fix

**Problem**: `logger.info()` (stderr, unbuffered) and `print()` (stdout, line-buffered
when piped) caused interleaved output where the next question's log appeared
during the current question's iteration.

**Fix**: Added `flush=True` to all `print()` calls in verbose agent output
(`rag/mcp_agent.py`) and evaluation progress (`scripts/eval/evaluate.py`).

### 5.2 Unnecessary Fact Proposal in Config B

**Problem**: When Config B detected a knowledge gap, the agent still executed
the full proposal/deduplication/validation pipeline, printing "KNOWLEDGE GAP
DETECTED" and "Proposed facts" messages, wasting LLM calls.

**Fix**: Reorganized `rag/mcp_agent.py` to check `enable_validation` early.
When validation is disabled and a knowledge gap is detected, the agent now
immediately returns a refusal: `"I don't have sufficient information...\nstatus: Refused"`,
skipping all proposal-related work.

### 5.3 Conservative INSUFFICIENT Assessment

**Problem**: The `knowledge_assessment.txt` prompt instructed the LLM to
assess for a "complete, factually accurate answer," causing it to compare KG
facts against its own broader knowledge. This led to constant INSUFFICIENT
assessments even when the KG had relevant facts, triggering unnecessary
proposal loops in Config B.

**Fix**: Created `knowledge_assessment_no_validation.txt` for Config B that
instructs the LLM to assess sufficiency based only on available facts, not
its external knowledge. `_get_assessment_prompt()` routes to the appropriate
prompt based on `enable_validation`.

**Impact**: Config B Gold Recall improved from 0.563 to 0.669 (+18.7%),
Answer Rate from 74.6% to 90.2% (+20.9%).

### 5.4 Thought Block Handling

**Problem**: Gemma 4 models wrap reasoning in `<thought>...</thought>` blocks.
The `status:` line (required for evaluation) was sometimes inside the thought
block or displaced by it, causing FMT_FAIL errors.

**Fix**:
- Added `_strip_thought_blocks()` utility to both `rag/mcp_agent.py` and
  `scripts/eval/evaluate.py`
- `is_refusal()` and `_strip_status_line()` now strip thought blocks before
  parsing
- Updated answer generation prompts to explicitly instruct the LLM to place
  the `status:` line as the last line, outside any `<thought>` blocks
- Added `SHOW_THOUGHT_BLOCKS` environment variable (default `false`) to
  control verbose output

**Impact**: FMT_FAIL dropped from multiple occurrences to 0 across all runs.

## 6. Evaluation Design

The evaluation is built on three deliberate choices: a **2-tier
drug-aware split**, **tier-aware QA generation**, and a single
**Gold Recall** metric. Each choice trades simplicity for a sharper
diagnostic signal between Config B (no validation) and Config C (dual-LLM
validation).

### 6.1 Two-Tier Drug-Aware Split

`scripts/eval/split_primekb.py` produces an entity-disjoint train/test
split where every test drug is assigned to one of two tiers. The full
algorithm has four stages, each controlled by a CLI hyperparameter that
shows up in `data/eval/split_stats.json` for reproducibility:

| Stage | Purpose | Hyperparameter | Default |
|-------|---------|----------------|--------:|
| 1. Drug-aware row sampling | Cap input size while preserving multi-triple drug groups (naive row sampling would leave most drugs with a single triple per relation, making the Partial tier infeasible) | `--max-rows` | `1000` |
| 2. Per-relation entity-disjoint split | Guarantee that no drug appears in both train and test for the same relation, so test gold answers cannot leak via the same drug | `--test-ratio` | `0.20` |
| 3. Test-drug tier assignment | Send some test drugs to **Full** (all gold triples in Neo4j) and the rest to **Partial** (some triples held out). Drugs with only one triple for a relation cannot be split and are forced to Full. | `--full-ratio` | `0.30` |
| 4. Per-drug held-out selection | For each Partial drug, decide which of its triples are *kept* in train vs. *held out* of train. `int()` truncation in `n_keep = int(len * partial_include)` ensures Partial drugs with ≥ 2 triples always have at least one held-out answer. | `--partial-include` | `0.50` |

Tier semantics, after all four stages have run:

| Tier | Neo4j coverage | What `tier_assignments.json` records | Diagnostic value |
|------|---------------|---------------------------------------|------------------|
| **Full** | All gold triples present in `train.csv` (= Neo4j) | `kg_answers = gold_answers`, `held_out_answers = []` | Tests pure retrieval -- can the system find what's there? |
| **Partial** | A subset of gold triples in `train.csv`; the rest only in `test.csv` | `kg_answers ⊊ gold_answers`, `held_out_answers = gold_answers \ kg_answers` | Tests knowledge-gap recovery -- can Config C surface the held-out answers via dual-LLM validation? |

**Why this layout drives the Config B vs Config C comparison.** On
Full-tier questions both configs should approach Gold Recall ≈ 1.0 (and
empirically do: 0.99 / 0.99 in Run 3). On Partial-tier questions,
Config B's Gold Recall is bounded above by the fraction of gold answers
already in Neo4j (`|kg_answers| / |gold_answers|`); only Config C's
propose/validate cycle can raise that ceiling by recovering
`held_out_answers`. The per-tier Gold Recall delta is therefore the
clean recovery signal that motivates the entire validation pipeline.

**Why entity-disjoint *per relation*?** Stage 2 is the load-bearing
choice -- without it, the tiering in Stage 3 and the metric in §4 lose
their meaning:

1. **No same-drug leakage.** If drug *D* appeared in both `train.csv`
   (some triples) and `test.csv` (others), then *D*'s training triples
   would land in Neo4j *and* serve as gold answers for the test question
   about *D*. Config B's KG search would always find them, pinning
   Gold Recall at ≈ 1.0 regardless of recovery ability.
2. **Bounded retrieval ceiling.** Disjointness guarantees every triple
   in `held_out_answers` is *absent* from Neo4j for that relation
   direction, so Config B's recall is mechanically capped at
   `|kg_answers| / |gold_answers|` and the lift to Config C is a clean
   measurement of the propose/validate loop, not noise from leaked
   edges.
3. **Per-relation, not global.** A drug can be train-only for
   `indication` and test-only for `contraindication` -- each call to
   `entity_disjoint_split()` runs independently. This keeps the
   relation-level Gold Recall rows in §3 comparable: each row reports
   recovery on truly unseen edges of that semantic type.
4. **Reverse-direction safety.** Reverse questions ("which drugs
   target disease *X*?") inherit the most-restrictive tier across
   contributing drugs (Stage 3). Without per-relation disjointness on
   the forward side, a Partial reverse question could be silently
   "answered" by retrieving a Full-tier neighbour's training triples,
   leaking the gold via a different traversal path.

In short, entity-disjointness per relation is what turns Gold Recall
from a memorisation score into a knowledge-recovery score -- and the
report's per-tier and per-relation breakdowns rely on it.

**`tier_assignments.json` schema:**

```jsonc
{
  "<drug>": {
    "<relation>": {
      "tier":             "full" | "partial",
      "kg_answers":       [...],   // in train.csv ⇒ retrievable from Neo4j
      "held_out_answers": [...]    // in test.csv only ⇒ recovery target
    }
  }
}
```

This file is the *only* source of truth for what is and is not in the KG
during evaluation. Every QA record in `qa_dataset.json` carries a copy
of these three fields so the evaluator can score Gold Recall and
Hallucination without re-reading the splits.

**Reproducibility.** All randomness flows from a single `--seed`
(default `42`); same seed + same input + same hyperparameters produce
byte-identical `train.csv`, `test.csv`, and `tier_assignments.json`. The
hyperparameters are captured in `split_stats.json` and surfaced in the
evaluation report filename (e.g. `f30_p70` ⇒ `--full-ratio 0.30`).

### 6.2 Tier-Aware QA Generation

`scripts/eval/generate_qa.py` derives QA pairs deterministically from
`test.csv` and `tier_assignments.json`. The LLM only writes the question
text -- gold sets are not LLM-derived.

For each relation the test triples are grouped twice: once by `x_name`
(forward, drug → diseases) and once by `y_name` (reverse, disease →
drugs). Each entity in each direction becomes one QA record, and the
prompt routing depends on the entity's tier:

| Tier prompt set | Used when | Style |
|-----------------|-----------|-------|
| `RELATION_CONTEXT`         | Entity is **Full** for that relation | Standard phrasing ("What is *Drug X* indicated for?") |
| `PARTIAL_RELATION_CONTEXT` | Entity is **Partial** for that relation | Completeness-demanding ("List **ALL** conditions...", "Provide a comprehensive list of every drug...") |

The completeness-demanding phrasing for Partial questions is engineered
to make the agent's INSUFFICIENT assessment fire -- which causes Config B
to refuse and Config C to enter the propose/validate cycle. Without
that phrasing, an LLM that already has parametric knowledge of the
domain will happily answer from KG facts alone and hide the
knowledge-gap signal.

**Reverse-direction tier inheritance.** A reverse question is keyed on a
disease, which has no direct entry in `tier_assignments.json`. The
script aggregates the tiers of the contributing drugs and applies the
rule: *if any drug in the gold answer set is Partial, the question is
Partial*. This mirrors the system's actual recovery task -- one missing
drug in the KG already turns the reverse question into a knowledge-gap
test.

If the LLM batch call fails or returns malformed JSON for a particular
entity, the script falls back to a deterministic template
(`FALLBACK_TEMPLATES` for Full, `PARTIAL_FALLBACK_TEMPLATES` for
Partial), so a single API hiccup never blocks the rest of the dataset.

The output file (`qa_dataset.json`) doubles as an incremental cache:
already-generated `(entity, relation, direction)` triples are skipped on
restart, and IDs are reassigned contiguously after the final batch.

### 6.3 Gold Recall Metric

Earlier runs reported Exact Match (binary -- *did the prediction
contain at least one gold answer?*) and KG Recall (only the fraction of
`kg_answers` recovered). Both were replaced with a single **Gold
Recall**:

```
gold_recall = count(gold_answers found in prediction) / count(all gold_answers)
```

Why one metric is enough:

- For Full-tier questions, `gold_answers == kg_answers`, so KG Recall
  and Gold Recall coincide -- nothing is lost.
- For Partial-tier questions, Gold Recall is strictly more informative
  than KG Recall: it counts recovered held-out answers, which is exactly
  the Config C signal we care about.
- Gold Recall ≥ Exact Match by definition (`exact_match = (gold_recall >
  0)`), and it provides graded credit instead of a binary verdict, so
  small improvements (e.g. recovering one of two held-out answers) are
  visible.

The `recovery_rate` metric was also dropped because the gap between
Config B and Config C Gold Recall on Partial-tier questions *is* the
recovery signal -- a separate metric would just restate the same
information.

### 6.4 Format Failure Handling

The evaluator expects each LLM answer to contain a `status:
Accepted/Refused` line. When missing (e.g., from thought block
interference), the question is retried up to 3 times. If all retries
fail, it is marked as a format failure and excluded from standard
metrics but reported separately.

## 7. Retrieval Pipeline

The hybrid search pipeline in `_search_kg()` (`rag/mcp_neo4j_server.py`)
combines four strategies:

1. **Vector similarity search** (`neo4j_store.search()`): Embeds the question
   with BAAI/bge-small-en-v1.5 and queries Neo4j's vector index for the top-k
   triplets by cosine similarity. Runs locally, no API call needed.

2. **LLM entity extraction** (`_extract_entity_names()`): Calls the primary
   LLM to extract biomedical entity names from the question (e.g., `["pyoureter"]`).
   Falls back to regex heuristic on timeout/failure.

3. **Exact graph lookup** (`neo4j_store.graph_search()`): Cypher
   case-insensitive exact match on extracted entity names against both subject
   and object fields.

4. **Fuzzy fallback** (`neo4j_store.fuzzy_entity_search()`): Checks if any
   stored entity name is a substring of the raw question text. Only used when
   the exact lookup returns nothing.

Results from all four are merged, deduplicated, and sorted by score.

### Heuristic Entity Extraction

When the LLM entity extraction times out, `_extract_entity_names_heuristic()`
uses three regex patterns:

- **Pattern 1**: Capitalized words (drug names like `Metformin`, `Diclofenac`)
- **Pattern 2**: Lowercase phrases after prepositions ("of", "for", "treating")
- **Pattern 3**: Multi-word lowercase biomedical terms (e.g., "endogenous depression")

## 8. Operational Notes

### API Rate Limits

Google AI Studio's free tier imposes strict rate limits. Config C makes 4-8
API calls per question (assessment, proposal, validation, re-assessment,
answer, persistence justification), so 194 questions can hit limits
frequently. Strategies:

- **HTTP timeout**: Set via `OPENAI_HTTP_TIMEOUT` (default 600s, recommended
  300-600s for evaluation). The SDK's default 600s combined with 3 retries
  means ~30 minutes wasted per exhausted retry at the default.
- **Tmux**: Always run evaluations in tmux to survive SSH/Cursor disconnection.
  Cursor's shell processes are killed when Cursor exits despite showing `?`
  as TTY.
- **Supplementary runs**: Use `--questions` flag to re-run only failed
  questions, then merge with `scripts/eval/merge_eval_reports.py`.

### Neo4j State

Config C persists validated triplets to Neo4j during evaluation. When
comparing Config B and Config C, always start from a clean Neo4j:

```bash
python scripts/import_primekb_to_neo4j.py --input data/eval/train.csv --clear
```

Or use `scripts/eval/run_eval_clean.sh` which handles clearing automatically.

## 9. Key Findings

1. **Config C's validation loop provides a meaningful +7.7% Gold Recall
   improvement** over Config B, with the biggest impact on off-label use
   (+61.2% relative) and partial-tier questions (+7.1pp).

2. **The validation loop is most valuable when the KG is sparse.** Off-label
   use relationships have the least coverage in PrimeKG, and Config C nearly
   doubles recall there (0.589 -> 0.950).

3. **Config B improved dramatically (+18.7% GR)** after the assessment prompt
   fix, which stopped the LLM from incorrectly marking relevant facts as
   INSUFFICIENT.

4. **Config C is remarkably stable across primary models** (~0.72 GR whether
   using Qwen-7B local or Gemma-4-26b remote), suggesting the validation LLM
   (gemma-4-31b-it) is the dominant factor.

5. **Hallucination is near-zero for both configs** (<0.1%), confirming the
   system rarely mentions gold answers without having them grounded in
   retrieved facts.

6. **The latency tradeoff is significant** (7.5x slower for Config C) but
   acceptable for batch evaluation. For interactive use, Config B provides
   strong results with much lower latency.

7. **Full-tier performance is near-perfect** (~0.99 GR for both configs),
   validating that the hybrid retrieval pipeline (vector search + entity
   extraction + graph lookup + fuzzy fallback) effectively retrieves facts
   when they exist in Neo4j.
